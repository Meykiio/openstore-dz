# Dashboard Steps Only the Account Owner Can Do

A coding agent has no access to the user's Guepex account. Everything below
happens by the user logging into their own dashboard — you cannot automate,
script, or shortcut any of it. Give the user this list at the point in the
build where each step actually becomes necessary, rather than all seven at
once up front — it lands better as "you need X now" than a wall of setup.

## 1. Generate API credentials (needed before any API call works)

In the **Développement** page of the dashboard:
- Generate the **API ID** and **API TOKEN**.
- The token is shown **only once**, at generation/regeneration time — the
  user must copy it immediately into their password manager or directly
  into their server's env file. If they lose it, they have to regenerate
  (which invalidates the old one).
- Credentials **expire after 365 days** and must be regenerated before then
  or API access stops working — worth a calendar reminder for the user, not
  something you can automate from code.
- Tell the user: put these straight into your `.env` file as
  `YALIDINE_API_ID` and `YALIDINE_API_TOKEN` — never paste them into chat,
  a screenshot, or a shared doc.

## 2. Choose an IP for quota monitoring (optional, dashboard-only)

The same Développement page lets them pick a source IP to view real-time
quota usage for. This is just visibility — not required for the
integration to function, but useful for the user to know it exists if
they hit rate limits later.

## 3. Prepare and deploy the webhook endpoint (your job)

Before the user can create a webhook, your code's endpoint must already be
deployed and answering the CRC challenge correctly (see
`webhooks-reference.md`). Tell the user once it's live and you've confirmed
it locally (e.g. curl the CRC check yourself if the endpoint is reachable).

## 4. Create the webhook (dashboard-only, after step 3)

In the **Webhooks** page:
- Click **Ajouter** (Add).
- Fill in: a recognizable name, the HTTPS URL of the deployed endpoint, an
  alert email (for delivery-failure notices), and which event types to
  subscribe to (`parcel_created`, `parcel_edited`, `parcel_deleted`,
  `parcel_status_updated`, `parcel_payment_updated`).
- On submit, Guepex validates the URL via the CRC check. If your endpoint
  isn't live yet or doesn't echo the token correctly, creation fails —
  double check step 3 first.
- The webhook is created **disabled** by default.

## 5. Copy the webhook secret key into env vars (dashboard-only)

The webhook's **secret key** is shown on its card in the Webhooks
Dashboard. The user copies it into `YALIDINE_WEBHOOK_SECRET` in their env
file — same rule as the API token: never share it in chat or a screenshot.
It can be regenerated from the same page if it's ever exposed.

## 6. Test, then enable (dashboard-only)

- Use the **Faire des tests** (Run tests) button to send a sample payload
  of each subscribed event type to the live endpoint and confirm it's
  handled correctly.
- Once tests pass, use **Changer l'état** (Change status) to flip the
  webhook to **Actif**. Only active webhooks deliver real events.

## 7. Ongoing maintenance (dashboard-only, can't be scripted)

- If the endpoint goes down for multiple days, Yalidine emails the alert
  address and eventually auto-disables the webhook — the user has to
  manually re-enable it from the dashboard after fixing the issue (there's
  a "Retirer le retardement" / remove-delay button if retries were
  paused).
- Delivery logs are only visible in the dashboard (48-hour retention) —
  point the user there when debugging a specific missed/failed delivery
  rather than trying to reconstruct it from your own server alone.
- API credentials expire yearly and must be regenerated by the user before
  expiry.

---

**If a user shares dashboard screenshots or pastes raw key/token/secret
values into the conversation:** use them only to understand what the UI
looks like or to confirm setup is correct if asked — never copy the actual
credential strings into code, files, commit messages, or anything you
generate. Point them to putting the real values directly into their env
file instead.
